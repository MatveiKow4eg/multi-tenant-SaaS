# UI/UX спецификация сервиса для B2B-лидогенерации и email-кампаний

## 1. Назначение документа

Этот документ описывает структуру интерфейса веб-приложения для B2B-лидогенерации, поиска компаний и контактов, а также для запуска email-кампаний по собственной базе пользователя или по базе, собранной внутри сервиса.

Документ нужен как опора для:
- проектирования интерфейса;
- постановки задач дизайнеру;
- постановки задач frontend-разработке;
- выстраивания единой UX-логики продукта;
- подготовки wireframes, mockups и дизайн-системы.

---

## 2. Продуктовая логика

Сервис состоит из двух главных функциональных зон:

### 2.1 Search / AI Search
Модуль для поиска компаний и контактов.

Основные задачи:
- пользователь формулирует запрос;
- система находит релевантные компании;
- показывает карточки фирм;
- дополняет их данными;
- при необходимости находит контакты;
- помогает оценить релевантность и отсортировать результаты.

### 2.2 Campaigns / Mass Mailing
Модуль для массовой рассылки.

Основные задачи:
- пользователь загружает собственную базу email-адресов или использует контакты из Search;
- система валидирует базу;
- пользователь создает шаблон письма;
- система готовит кампанию;
- пользователь отправляет рассылку;
- система собирает доставляемость, ответы и аналитику.

### 2.3 Общий принцип продукта
Интерфейс должен строиться вокруг двух больших сценариев:
1. **Найти компании и контакты**.
2. **Подготовить и запустить email-кампанию**.

Нельзя смешивать оба сценария в одном хаотичном экране. Они должны быть связаны, но ясно разделены.

## 3. Общий стиль интерфейса

### 3.1 Визуальный характер
Рекомендуемый стиль:
- чистый B2B SaaS интерфейс;
- светлая тема как основная;
- акцент на структуре и читаемости;
- минимум визуального шума;
- много воздуха;
- ясные таблицы;
- сильная иерархия заголовков и блоков;
- строгий рабочий вид, а не «маркетинговый лэндинг внутри кабинета».

### 3.2 Что нельзя делать
Не рекомендуется:
- кислотные цвета;
- сложные градиенты в рабочем интерфейсе;
- бесполезные большие карточки без данных;
- слишком много анимаций;
- перегруженные дашборды с десятками метрик;
- перегруженные формы без логической группировки;
- хаотичное количество кнопок в одной зоне.

### 3.3 Что нужно сделать хорошо
Нужно сделать особенно качественно:
- таблицы и фильтры;
- боковые панели с деталями;
- статусы и бейджи;
- многошаговые мастера действий;
- превью перед запуском;
- блоки предупреждений и системных ошибок;
- понятную логику состояний данных.

## 4. Цветовая схема

### 4.1 Базовая палитра
Рекомендуемая базовая схема:
- фон приложения: светло-серый или почти белый;
- карточки: белые;
- текст: графитовый;
- вторичный текст: нейтрально-серый;
- бордеры: светло-серые;
- основной акцент: синий или темно-сине-зеленый.

Пример логики:
- Основной фон: `#F7F8FA`
- Поверхность карточек: `#FFFFFF`
- Основной текст: `#111827`
- Вторичный текст: `#6B7280`
- Бордер: `#E5E7EB`
- Primary accent: `#2563EB`

### 4.2 Цвета состояний
- Успех: зеленый
- Предупреждение: оранжевый
- Ошибка/риск: красный
- Информационный статус: синий
- Черновой/неактивный: серый

Примеры использования:
- **Verified** — зеленый
- **Pending** — оранжевый
- **Failed** — красный
- **Draft** — серый
- **Running** — синий

## 5. Базовый layout приложения

### 5.1 Общая структура
Рекомендуемая структура экрана:
- слева постоянный sidebar;
- сверху topbar;
- справа основная рабочая область;
- внутри страниц — карточки, таблицы, фильтры, боковые панели и модальные окна.

### 5.2 Sidebar
Основные разделы навигации:
- Dashboard
- Search
- Companies
- Contacts
- Lists
- Campaigns
- Inbox / Replies
- Analytics
- Settings
- Billing

### 5.3 Topbar
В верхней панели должны находиться:
- переключатель tenant / workspace;
- глобальный поиск по сервису;
- usage/credits индикатор;
- уведомления;
- профиль пользователя;
- быстрые действия.

### 5.4 Рабочая область
Внутри контента у страницы должна быть понятная структура:
- title + description;
- primary action;
- secondary actions;
- content area;
- filter area;
- status area / alerts.

## 6. Dashboard

### 6.1 Цель страницы
Dashboard должен отвечать на вопрос:
**«Что происходит в системе прямо сейчас?»**

Это не декоративная страница, а рабочая операционная панель.

### 6.2 Основные блоки

#### Блок A. KPI overview
В верхней части:
- найдено компаний;
- найдено контактов;
- активные кампании;
- reply rate;
- positive replies;
- usage за текущий период.

Каждая карточка должна содержать:
- название метрики;
- текущее значение;
- изменение относительно прошлого периода;
- дополнительную подпись.

#### Блок B. Главные действия
Две крупные action-card зоны:
- **AI Search**
- **Email Campaigns**

Внутри каждой:
- заголовок;
- краткое описание;
- основная кнопка действия.

Пример:
- AI Search → «Найти компании»
- Email Campaigns → «Создать кампанию»

#### Блок C. Recent activity
Список последних действий:
- последние search jobs;
- последние кампании;
- последние ответы;
- последние импорты баз.

#### Блок D. System alerts
Предупреждения:
- домен не верифицирован;
- SPF/DKIM/DMARC не настроены;
- заканчиваются credits;
- высокий bounce rate;
- активные кампании поставлены на паузу;
- требуются действия по безопасности.

### 6.3 UX-особенности
- Dashboard должен быстро читаться за 10–15 секунд.
- Главные сценарии должны быть доступны без прокрутки.
- Числа и статусы важнее графического декора.

## 7. Search

### 7.1 Цель страницы
Это главный рабочий экран поиска компаний.

Пользователь должен иметь возможность:
- сформулировать поисковый запрос;
- получить результаты;
- уточнить их фильтрами;
- открыть детали компании;
- сохранить результаты в список;
- передать найденные контакты в кампанию.

### 7.2 Основные блоки

#### Блок A. AI Search Bar
Большая строка ввода сверху.

Назначение:
- пользователь описывает, какие компании ему нужны;
- система обрабатывает свободный текстовый запрос.

Примеры подсказок:
- «бетонные фирмы в Литве»
- «металлообработка в Эстонии»
- «строительные компании Финляндии 20–200 сотрудников»

Рядом должны быть:
- primary button «Найти»;
- secondary button «Глубокий поиск»;
- индикатор примерной стоимости или credits.

#### Блок B. Filters panel
Фильтры слева или сверху.

Основные фильтры:
- страна;
- регион/город;
- отрасль;
- размер компании;
- наличие сайта;
- наличие email;
- наличие контактов;
- статус проверки;
- источник;
- дата добавления;
- score/relevance.

#### Блок C. Results table
Результаты лучше показывать в виде таблицы.

Колонки:
- Company
- Country
- Industry
- Size
- Website
- Contacts
- Relevance score
- Source
- Status

Должны поддерживаться:
- сортировка;
- bulk selection;
- multi-select действия;
- сохранение фильтров;
- сохраненные views.

#### Блок D. Company detail drawer
При клике по компании справа открывается боковая панель.

Содержимое:
- название компании;
- краткое описание;
- сайт;
- отрасль;
- размер;
- страна;
- сигналы;
- summary;
- найденные контакты;
- причина релевантности.

Кнопки:
- «Добавить в список»;
- «Открыть карточку компании»;
- «Создать кампанию»;
- «Запустить enrichment».

### 7.3 Состояния страницы
Нужно продумать состояния:
- пустая выдача до первого поиска;
- процесс поиска;
- результаты найдены;
- результатов нет;
- ошибка провайдера;
- частично найденные данные;
- превышен budget/credits.

### 7.4 UX-акценты
- Поиск должен быть простым для новичка.
- Пользователь не должен теряться между строкой поиска и таблицей.
- Важно показывать, к чему относится каждая компания.
- Категория, страна, отрасль и релевантность должны быть видны сразу.

## 8. Companies

### 8.1 Цель страницы
Это внутренняя база компаний пользователя.

Разница со Search:
- Search показывает найденные результаты;
- Companies — это уже сохраненная база и рабочий каталог.

### 8.2 Основные блоки

#### Блок A. Header
Верх страницы:
- название раздела;
- количество компаний;
- кнопки импорта/экспорта;
- кнопка добавления в список;
- кнопка запуска enrichment.

#### Блок B. Saved views
Например:
- Все компании
- Горячие лиды
- Без контактов
- Нужна проверка
- Для кампаний
- Добавлены недавно

#### Блок C. Table
Основная таблица компаний.

Колонки:
- Company
- Industry
- Country
- Size
- Contacts count
- Status
- Lead score
- Last activity
- Source

#### Блок D. Bulk actions
Действия над выбранными строками:
- добавить в список;
- экспортировать;
- обновить enrichment;
- создать кампанию;
- изменить статус;
- добавить теги.

### 8.3 Страница карточки компании
Внутри карточки компании должны быть вкладки:
- Overview
- Contacts
- Activity
- Campaigns
- Notes
- AI Insights

#### Overview
Содержит:
- summary компании;
- сайт;
- домен;
- отрасль;
- размер;
- страна;
- дата добавления;
- source;
- last enrichment;
- why relevant.

#### Contacts
Таблица контактов компании:
- имя;
- должность;
- email;
- phone;
- linkedin;
- verification status.

#### Activity
История действий:
- найдено;
- enriched;
- добавлено в список;
- использовано в кампании;
- получен ответ.

#### Campaigns
Показывает, в каких кампаниях участвовала компания.

#### Notes
Заметки пользователя и команды.

#### AI Insights
Результаты AI-анализа:
- relevance score;
- reason;
- confidence;
- suggested next step.

Отдельный каталог контактов.

Многие пользователи мыслят не компаниями, а конкретными email-контактами, поэтому контактам нужен собственный раздел.

### 9.2 Таблица контактов
Колонки:
- Name
- Title
- Company
- Email
- Email status
- Phone
- Country
- Source
- Last contacted
- Campaign status

### 9.3 Фильтры
- verified only;
- with email;
- with phone;
- not contacted;
- bounced;
- unsubscribed;
- by company;
- by campaign;
- by source.

### 9.4 Действия
- добавить в список;
- экспортировать;
- отправить в кампанию;
- обновить статус;
- удалить;
- обновить данные.

## 10. Lists

### 10.1 Цель страницы
Lists — промежуточный уровень между Search, Companies и Campaigns.

Именно здесь пользователь формирует рабочие сегменты для дальнейших действий.

### 10.2 Что такое список
Список может быть:
- списком компаний;
- списком контактов;
- сегментом под кампанию;
- временной подборкой.

### 10.3 Основные блоки

#### Блок A. Lists table
Поля:
- name;
- type;
- records count;
- owner;
- updated at;
- source.

#### Блок B. List detail
Внутри списка:
- участники списка;
- фильтры, по которым он собран;
- дата последнего обновления;
- теги;
- действия.

#### Блок C. Actions
- экспорт;
- создать кампанию;
- обновить данные;
- переименовать;
- объединить;
- duplicate list;
- delete list.

### 10.4 UX-идея
Списки должны быть очень понятными и простыми. Это один из ключевых мостов между поиском и рассылками.

## 11. Campaigns

### 11.1 Цель страницы
Campaigns — второй главный модуль продукта.

Он должен позволять:
- загружать собственную базу;
- использовать найденные контакты;
- создавать шаблон письма;
- подготавливать кампанию;
- отправлять письма;
- отслеживать результаты.

### 11.2 Список кампаний
Колонки:
- campaign name;
- status;
- audience size;
- sent;
- delivered;
- replies;
- positive replies;
- bounce rate;
- created by;
- created at.

Статусы:
- Draft
- Prepared
- Running
- Paused
- Completed
- Failed

### 11.3 Campaign creation wizard
Кампанию лучше создавать не на одном экране, а через wizard.

#### Шаг 1. Выбор источника аудитории
Варианты:
- из Search/Lists;
- из Contacts;
- загрузка CSV/XLSX;
- импорт из CRM позже.

#### Шаг 2. Проверка базы
Система должна показать:
- всего записей;
- валидных email;
- дубликатов;
- invalid email;
- unsubscribed;
- suppressed;
- skipped records.

#### Шаг 3. Настройка шаблона
Элементы экрана:
- subject editor;
- email body editor;
- preview pane;
- переменные шаблона;
- A/B варианты опционально.

Переменные:
- `{first_name}`
- `{company_name}`
- `{country}`
- `{industry}`

#### Шаг 4. Настройка отправки
Параметры:
- отправляющий домен;
- mailbox;
- дневной лимит;
- скорость отправки;
- расписание;
- timezone;
- reply handling.

#### Шаг 5. Review
Показывать:
- размер аудитории;
- с какого домена идет отправка;
- estimated duration;
- estimated credits/cost;
- warnings;
- deliverability risk;
- количество пропущенных адресов.

#### Шаг 6. Prepare vs Send
Ключевая UX-фишка:
- одна кнопка должна **подготовить** кампанию;
- отдельная кнопка должна **отправить** кампанию.

Это позволяет:
- сначала проверить всё;
- потом подтвердить запуск;
- избежать случайной отправки.

### 11.4 Campaign detail page
Блоки страницы:
- общий overview;
- статистика;
- шаблон;
- аудитория;
- события;
- ответы;
- warning/health status.

### 11.5 Критически важные элементы для Campaigns
Обязательно должны быть:
- suppression list integration;
- unsubscribe handling;
- bounce handling;
- deliverability risk indicators;
- доменные и mailbox лимиты;
- пауза кампании;
- ручной restart.

## 12. Inbox / Replies

### 12.1 Цель страницы
Это рабочий inbox для обработки входящих ответов.

Он должен помогать команде:
- видеть новые ответы;
- быстро понимать смысл;
- отличать позитивные ответы от отказов;
- принимать следующие действия.

### 12.2 Основная структура

#### Левая колонка
Список тредов/ответов.

Фильтры:
- New
- Positive
- Neutral
- Objection
- Auto-reply
- Unsubscribe
- Spam-risk
- Closed

#### Центральная зона
Содержимое переписки:
- исходное письмо;
- ответ клиента;
- история треда.

#### Правая панель
Контекст и действия:
- AI summary;
- sentiment/category;
- suggested reply;
- company info;
- campaign info;
- owner;
- status;
- next step.

### 12.3 Статусы
- New
- Reviewed
- Needs reply
- Awaiting
- Closed
- Booked

### 12.4 UX-акценты
- Нужно минимизировать хаос.
- Пользователь должен быстро понять, какие ответы важные.
- Приоритетные положительные ответы должны быть наверху.

## 13. Analytics

### 13.1 Цель страницы
Аналитика должна показывать эффективность, а не просто набор чисел.

Главный вопрос:
**«Какие действия приводят к ответам и встречам?»**

### 13.2 Основные блоки

#### Блок A. KPI row
- sent;
- delivered;
- bounced;
- reply rate;
- positive reply rate;
- meetings booked.

#### Блок B. Time series
Графики по дням/неделям:
- отправка;
- replies;
- positive replies;
- bounce rate.

#### Блок C. Performance tables
- лучшие кампании;
- худшие кампании;
- лучшие шаблоны;
- лучшие сегменты;
- лучшие страны;
- лучшие отрасли.

#### Блок D. Deliverability health
- домены в риске;
- высокий bounce;
- высокий unsubscribe;
- паузы кампаний;
- предупреждения провайдера.

### 13.3 UX-правило
Не надо превращать Analytics в перегруженный BI-инструмент. Лучше меньше метрик, но реально полезных.

## 15. Domains / Mail Setup Wizard

### 15.1 Цель страницы
Это одна из самых критичных зон сервиса.

Пользователь должен уметь:
- добавить домен;
- пройти верификацию;
- настроить SPF/DKIM/DMARC;
- подключить mailbox;
- понимать статус готовности к отправке.

### 15.2 Структура страницы

#### Блок A. Domain list
Список доменов с колонками:
- domain;
- SPF;
- DKIM;
- DMARC;
- mailbox count;
- status;
- last checked.

#### Блок B. Domain detail
Внутри домена показывать:
- DNS записи;
- статус каждой записи;
- инструкции по настройке;
- подсказки по исправлению;
- кнопки re-check.

#### Блок C. Health panel
Показывать:
- domain verified;
- sending ready;
- warnings;
- reputation-related alerts позже.

### 15.3 Состояния
- Verified
- Pending
- Failed
- Needs action
- Checking

### 15.4 UX-идея
Это должен быть мастер с очень понятными шагами, а не техническая свалка.

## 17. Системные компоненты UI

### 17.1 Таблицы
Критичный компонент для всего продукта.

Требования:
- sticky header;

- фильтры;
- bulk selection;
- pagination;
- сохраненные views;
- column visibility;

### 17.2 Filters

- быстрые фильтры;

- reset all.

### 17.3 Drawers
Используются для:
- карточки компании;
- карточки контакта;

Используются для:
- подтверждения удаления;
- запуска действий;

### 17.5 Stepper/Wizard
Нужен для:

Единый компонент статусов нужен для:
- компаний;
- контактов;
- доменов;

### 17.7 Empty states
Нужны для:
- пустой Search;
- нет компаний;

## 18. Состояния данных и обратная связь системы

### 18.1 Loading
Для каждой тяжелой операции нужен понятный loading-state.

### 18.2 Processing jobs
Для jobs нужно показывать:
- queued;
- running;
- partially completed;
- completed;
- failed.

### 18.3 Errors
Ошибки должны быть человеческими, а не только техническими.

Примеры:
- «Не удалось завершить поиск. Попробуйте сузить запрос.»
- «Кампания не может быть отправлена: домен не верифицирован.»
- «У адреса нет валидного email.»

### 18.4 Warnings
Примеры предупреждений:
- «Высокий bounce risk»
- «Недостаточно credits»
- «Часть записей будет пропущена»
- «DMARC не настроен»

## 19. Онбординг нового пользователя

### 19.1 Цель
Пользователь должен быстро понять продукт и дойти до первого результата.

### 19.2 Предлагаемая логика онбординга
Шаги:
1. Создать workspace.
2. Пригласить команду опционально.
3. Выбрать основной сценарий:
   - найти компании;
   - загрузить базу и запустить кампанию.
4. Добавить домен позже или сразу.
5. Дойти до первого полезного результата.

### 19.3 Первый запуск
Лучше спросить:
- «Что вы хотите сделать первым?»
- «Найти компании»
- «Загрузить базу и отправить кампанию»

Это поможет сразу разделить пользователя по правильному сценарию.

## 20. Мобильная и адаптивная логика

### 20.1 Приоритет устройства
Основное устройство — desktop/laptop.

### 20.2 Mobile strategy
Полный рабочий функционал лучше ориентировать на desktop.

Для мобильной версии достаточно:
- dashboard quick view;
- просмотр компаний;
- просмотр replies;
- базовые уведомления;
- основные статусы.

Создание сложных кампаний и глубокий поиск лучше делать на desktop.

## 23. Итоговая концепция интерфейса

Продукт должен выглядеть как:
- серьезный B2B-инструмент;
- чистый data-driven SaaS;
- рабочая платформа с понятной структурой;
- смесь research, list-building и controlled outreach.

Главные свойства интерфейса:
- понятный sidebar;
- сильные таблицы;
- логичный переход от поиска к спискам;
- понятный мастер кампаний;
- аккуратный inbox;
- прозрачные статусы и предупреждения;
- контроль до отправки, а не хаотичный запуск.

Ключевое UX-обещание:
**Пользователь всегда должен понимать, где он сейчас, что делает система, что уже готово, что требует внимания и что будет следующим шагом.**
