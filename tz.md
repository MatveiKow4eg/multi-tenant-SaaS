1. Главная цель агента

Твой агент должен делать не “рассылку писем”, а полный цикл продаж до тёплого контакта:

находить подходящие заводы и компании;
понимать, подходят ли они тебе;
вытаскивать контакт;
писать первое письмо;
делать follow-up;
читать ответ;
определять смысл ответа;
передавать тебе только те кейсы, где уже есть шанс на разговор.

То есть агент не должен заменять тебя в переговорах. Он должен забирать на себя весь первый тяжёлый этап.

2. Что именно агент должен уметь

Раздели систему на 6 ролей.

Роль 1 — Finder
Ищет компании по ключам, странам и типу бизнеса.

Роль 2 — Researcher
Открывает сайт и собирает контекст: чем занимается компания, есть ли производство, есть ли вакансии, на каком языке сайт.

Роль 3 — Qualifier
Решает, подходит ли компания под твою модель.

Роль 4 — Outreach Writer
Пишет первое письмо и follow-up.

Роль 5 — Mail Operator
Отправляет письма, ставит follow-up, останавливает цепочку.

Роль 6 — Reply Analyst
Читает ответы и решает: интересно / неинтересно / позже / нужен ты.

Эти роли могут жить в одном проекте, но логически они должны быть разделены. Это сильно упростит отладку.

3. Финальный стек

Вот стек, который я бы жёстко утвердил:

Python
FastAPI
PostgreSQL
Redis
Celery
Playwright
OpenAI Responses API
Zone SMTP + IMAP

FastAPI официально описывается как modern, high-performance, production-ready web framework для Python API, а Celery — как distributed task queue с поддержкой real-time processing и task scheduling.

4. Общая архитектура

Система должна работать так:

База данных хранит компании, контакты, письма, ответы, статусы и blacklist.
Celery-воркеры гоняют фоновые задачи.
FastAPI даёт тебе API и внутреннюю админку.
Playwright открывает сайты и собирает данные.
OpenAI анализирует сайт, пишет письма и разбирает ответы.
Zone отправляет письма и принимает ответы.

5. Пошаговый план внедрения
Этап 1. Подготовить почтовую инфраструктуру

Сделай отдельный ящик для аутрича. Не мешай его с основной почтой.
Минимум:

sales@... или partnerships@...
лучше отдельный поддомен под outreach
включить SPF
включить DKIM
включить DMARC

Это нужно сделать до разработки логики рассылки, потому что без нормальной аутентификации даже хороший бот будет давать плохую доставляемость. Zone прямо пишет, что SPF, DKIM и DMARC нужны, чтобы письма не уходили в спам.

Этап 2. Поднять каркас проекта

Собираешь backend на Python:

FastAPI — API
Postgres — данные
Redis — брокер / кэш
Celery — фоновые задания
Playwright — сайты
OpenAI — ИИ-задачи

На этом этапе ещё не нужен красивый интерфейс. Достаточно, чтобы проект запускался, принимал задачи и писал их в базу. FastAPI и Celery для этого подходят как раз под production-подобную схему с API плюс очередями.

Этап 3. Спроектировать базу

Нужны такие таблицы:

companies
Хранит компанию: название, домен, страну, отрасль, score, статус.

company_pages
Сырые страницы сайта: url, тип страницы, текст, когда собрана.

contacts
Контакты: email, роль, источник, confidence.

campaigns
Одна цепочка контакта с одной компанией.

messages
Все письма: исходящие и входящие.

replies
Классификация ответов.

blacklist
Кому не писать.

schedules
Когда следующий follow-up.

audit_log
Что и почему решил бот.

Это нужно не ради “красоты”, а чтобы потом можно было понять, почему бот что-то сделал.

Этап 4. Сделать Finder

Первый живой модуль — поиск компаний.

Он должен:

брать список стран;
брать список ниш;
собирать результаты;
сохранять только уникальные домены;
сразу отбрасывать явный мусор.

Ищи по типам:

manufacturing
industrial
factory
plant
fabrication
welding
metal
production
subcontract manufacturing

На первом этапе не пытайся сделать суперумный поиск. Цель — чтобы бот стабильно находил кандидатов.

Этап 5. Сделать Researcher

После нахождения домена бот должен открыть сайт и собрать минимальное досье:

homepage
about
services
careers/jobs
contact
location
language hints

Playwright здесь нужен именно потому, что много сайтов грузятся скриптами, прячут контакты или строят DOM динамически; официально Playwright поддерживает reliable automation для scripting и AI agents.

На выходе у тебя должен появляться объект примерно такого вида:

company_name
domain
country
languages_found
pages_found
has_careers_page
industry_guess
contact_pages
text_summary
Этап 6. Подключить Qualifier

Вот здесь уже подключается ИИ.

Задача квалификатора:

определить, это завод/производство или нет;
определить нишу;
понять, есть ли признаки потребности в рабочей силе;
выбрать язык письма;
поставить score от 0 до 100.

Используй для этого структурированный JSON-output, а не свободный текст.
Например, агент должен возвращать:

{
  "is_relevant": true,
  "industry": "metal fabrication",
  "country": "Lithuania",
  "recommended_language": "lt",
  "signals": [
    "production company",
    "industrial equipment",
    "jobs page found"
  ],
  "score": 84,
  "reason": "manufacturing company with industrial hiring indicators"
}

Для таких задач GPT-5.4 логичен как основной reasoning-слой, а Responses API — как основной интерфейс интеграции. OpenAI прямо рекомендует для новых интеграций Responses API и отдельно выводит GPT-5.4 как стартовую модель для complex reasoning and coding.

Этап 7. Сделать Contact Resolver

После квалификации бот должен искать лучший контакт.

Приоритет такой:

HR / recruitment / careers
production / operations / procurement
general info@
contact form

По каждому контакту сохраняй:

email
имя
роль
страница, где найден
confidence

Очень важно: бот должен понимать разницу между “хороший контакт” и “контакт просто найден”.

Этап 8. Собрать Company Brief

Перед письмом агент должен сформировать краткий внутренний бриф:

кто это;
чем занимается;
почему подходит;
почему пишем именно сейчас;
кому пишем;
на каком языке;
какой CTA использовать.

Это внутренний слой. Его пользователь не видит. Но без него письма будут пустые и одинаковые.

Этап 9. Сделать Outreach Writer

Дальше агент пишет цепочку.

Минимум 3 шага:

Письмо 1
Короткое знакомство и предложение обсудить.

Follow-up 1
Через 3–5 дней. Мягкое напоминание.

Follow-up 2
Ещё через 5–7 дней. Последний короткий касание.

На вход генератору даёшь:

language
company brief
role of recipient
tone
max length
CTA type

На выходе:

subject
body_step_1
body_followup_1
body_followup_2

Здесь ИИ не должен “придумывать легенды”. Он должен только аккуратно персонализировать под контекст компании.

Этап 10. Сделать Mail Operator

Это один из самых важных модулей.

Он должен:

брать готовые письма из очереди;
отправлять через Zone SMTP;
логировать message_id;
ставить follow-up в расписание;
не отправлять повторно, если уже есть активная цепочка;
не отправлять, если домен в blacklist;
не отправлять, если был ответ.

Настройки Zone для SMTP и IMAP уже есть официально: smtp.zone.eu и imap.zone.eu с соответствующими портами и обязательной авторизацией.

Этап 11. Сделать Reply Ingestion

Бот должен регулярно читать входящие письма через IMAP в Zone.

Он должен вытаскивать:

from
subject
body
date
thread reference
attachments presence

Дальше привязывать ответ к кампании.

Если не удаётся привязать — складывать в отдельный “manual review”.

Этап 12. Сделать Reply Analyst

Это второй важнейший ИИ-модуль.

Он должен классифицировать ответы минимум на такие категории:

interested
ask_for_details
send_rates
not_now
not_interested
wrong_contact
auto_reply
out_of_office
forwarded_internal

И возвращать:

класс ответа;
короткую сводку;
нужен ли человек;
что делать дальше.

Пример результата:

{
  "label": "ask_for_details",
  "summary": "Contact asks for rates and conditions of cooperation.",
  "needs_human": true,
  "next_action": "notify_user"
}
Этап 13. Сделать Handoff тебе

Когда приходит тёплый ответ, бот должен не просто писать “есть письмо”, а создавать нормальную карточку:

компания;
страна;
сайт;
кто ответил;
их сообщение;
краткое резюме;
рекомендуемый ответ;
приоритет.

То есть ты должен заходить уже на подготовленный контакт, а не разбирать с нуля, что это вообще за фирма.

Этап 14. Сделать stop-логику

Вот это обязательно.

Бот должен немедленно остановить цепочку, если:

получен любой живой ответ;
контакт попросил не писать;
письмо bounced;
домен в blacklist;
компания уже в активном диалоге;
контакт признан неподходящим.

Без этой логики бот превращается в спам-машину.

Этап 15. Сделать дедупликацию

Проверка должна быть на трёх уровнях:

домен компании;
email;
активная кампания по компании.

Иначе бот будет писать:

на 3 адреса одной компании;
по одному и тому же домену разными цепочками;
повторно спустя короткое время.
Этап 16. Сделать логирование решений

Каждое важное действие записывать:

найден домен;
сайт собран;
score поставлен;
контакт найден;
письмо сгенерировано;
письмо отправлено;
follow-up поставлен;
ответ получен;
ответ классифицирован;
цепочка остановлена.

Это сильно помогает, когда через месяц ты начинаешь понимать, почему лидов много, а качества мало.

6. Какие модели ИИ использовать

Я бы делал так.

GPT-5.4
Для:

квалификации компании;
написания писем;
разбора живых ответов;
handoff summary.

Более дешёвая модель того же семейства
Для:

простых коротких задач;
рутинной классификации;
второстепенных summarization-задач.

OpenAI сейчас показывает семейство GPT-5.4, включая gpt-5.4, gpt-5.4-mini и gpt-5.4-nano, где mini и nano позиционируются как более дешёвые варианты для lower-latency / lower-cost workloads.

Практически это значит так:

важные решения — на gpt-5.4
дешёвые массовые мелочи — на gpt-5.4-mini
7. Что ИИ делать не должен

Ни в коем случае не отдавай ИИ:

дедупликацию;
расписание;
выбор “отправлять / не отправлять”, если это уже формальное правило;
blacklist;
лимиты отправки;
факт остановки цепочки после ответа.

Это должен делать обычный код.
ИИ нужен там, где есть неструктурированный текст и смысл, а не там, где есть чёткое правило.

9. Что считать первым рабочим результатом

Первый реальный успех — не “бот отправил 1000 писем”.

Первый успех — это когда он стабильно делает вот это:

находит новую компанию;
правильно понимает, что это твоя ниша;
находит контакт;
пишет нормальное письмо;
отправляет через Zone;
читает ответ;
правильно понимает, что ответ тёплый;
передаёт его тебе.

Вот это и есть MVP полного цикла.

10. Какие KPI смотреть

С самого начала смотри только на 6 цифр:

найдено компаний;
квалифицировано компаний;
найдено контактов;
отправлено писем;
получено ответов;
тёплых ответов.

Позже добавишь:

reply rate;
positive reply rate;
bounce rate;
сколько лидов дошло до звонка.
11. Ограничения на старте

На старте не надо делать:

10 языков;
50 шаблонов;
массовые объёмы;
сложную CRM;
красивую админку.

Надо сделать:

один язык или два;
один тип компаний;
1 основную цепочку;
стабильную доставку;
хороший разбор ответов.
12. Самые важные правила агента

Вот их можно прямо вставить в спецификацию.

Правило 1
Не отправлять письмо без qualification score.

Правило 2
Не отправлять follow-up, если был ответ.

Правило 3
Не писать повторно по домену, если там уже есть активная цепочка.

Правило 4
Любой “not interested” или “do not contact” сразу в blacklist.

Правило 5
Любой тёплый ответ сразу передавать человеку.

Правило 6
Все решения логировать.

13. Самое короткое описание всей системы

Если в одну фразу:

бот на Python ищет заводы, анализирует их сайты через ИИ, пишет персонализированные письма, отправляет их через Zone, делает follow-up, читает ответы по IMAP, классифицирует их и передаёт тебе только тёплые лиды.
